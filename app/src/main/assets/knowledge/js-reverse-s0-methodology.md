# Web JS 逆向 · 总纲与四阶段方法论（黑盒实战逆向 · 序章/第一章精编）

> 来源：ycoo.net《黑盒实战逆向》前言/序章 + 第一章「四阶段全知识体系手册」。本页是方法论地图，具体操作看 `js-reverse-s2-basic.md`（入门 SOP）与 `js-reverse-s2-booksource.md`（书源迁移）。

## 一、什么是黑盒逆向

在没有源代码的前提下，通过观察输入/输出、抓包、静态/动态分析，还原系统内部逻辑。对书源制作的直接意义：**目标站的数据接口、动态参数、加密签名都是黑盒，书源规则就是逆向结论的最终载体**。

完整路线：**理论准备 → 黑盒分析 → 深入逆向 → 验证输出**，四阶段环环相扣。

## 二、四阶段知识体系

### 阶段 1：理论准备
- 基础：HTTP/HTTPS 协议、Cookie/Session、字符编码、常见加密识别（MD5/SHA 常量、AES 的 S 盒、HMAC 双轮结构、Base64 特征）
- 核心观点：建立「分层心智模型」；签名逆向遵循「**先逆拼接规则，再确认算法，最后找 salt/key**」
- 环境：抓包工具 + 格式化/反混淆工具 + 可调试浏览器

### 阶段 2：黑盒分析（核心实战流程）
1. **侦察抓包**：定位数据接口；记录请求参数、头、Cookie；用「重放法」验证参数时效（改时间戳/页码看重放是否被拒）
2. **静态分析**：入口优先；关键词搜索（sign/encrypt/token/getSign）；字符串交叉引用
3. **动态调试**：断点 + Hook，抓「明文—密文」配对
4. **算法还原三路线**：标准库直接复现 / 模拟执行（不读懂混淆也能跑）/ 借页面环境 RPC 调用

### 阶段 3：深入逆向（高级对抗）
- 反调试、混淆（控制流平坦化——对策是 Hook 输入输出两端）、加壳脱壳
- 环境指纹检测、完整性校验
- 专题：传输层指纹（TLS/JA3）、服务端直连校验（本地伪造一律无效）

### 阶段 4：验证输出
- 「七步对齐法」逐段 diff：编码、字节序、填充、拼接顺序是最常见偏差源
- 用脚本复现算法并写 verify 函数对照真实响应
- 重放攻击测试：改时间戳/nonce/跨账号验证签名绑定关系
- 归档：目标文件、参数结论、失败尝试（试错路标）、可运行脚本、坑清单

## 三、实战一案例教训（换脸 AI 谷歌硬件锁，4 天 440 轮）

逆向 RemakeFace AI（Play Integrity 保护）的最终结论，对书源工作同样适用：

1. **攻击面要选对**：破解组死磕本地签名校验全灭，因为服务端会验证书链——「他们以为锁在门上，其实锁在银行金库里」。做书源同理：不要在错误层硬刚（如本地伪造 TLS 指纹），先判断防线在哪一层。
2. **三条攻击路线按成本排序**：中间人伪造（最省事，易被会话校验堵）→ 绕过认证（成本高、易被服务端直连堵）→ 请求签名复现（最彻底，但可能撞硬件信任根）。
3. **知道何时止损**：遇到硬件信任根/服务端直连 Google 这类不可绕过的层，「最后不是输给技术，是输给物理」。书源场景对应：遇到强 WAF/设备级校验，改用 WebView 通道（本 App 的 `browser_verify` + `set_domain_mode`）而不是死磕协议复现。
4. **风控是真实成本**：429 长冷却（24h）、IP 封禁贯穿全程。调试期控制请求频率，批量探测同一反爬端点会触发风控。

## 四、贯穿主线

「逆向的尽头是架构决策」——多数站点不需要走到阶段 3。书源场景的经验比例：80% 的站点在阶段 2（抓包 + 规则）就能完成；15% 需要简单 JS 还原（eval_js 可验证）；只有 5% 涉及混淆/指纹/设备校验，这时优先换通道（WebView/验证中心），不是硬逆。
